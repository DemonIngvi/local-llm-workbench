Product brief

Проблема: локальные модели, шлюз и различные агентные среды сложно согласованно запускать и переключать.

Пользователь: разработчик одного компьютера Windows/WSL или Linux. Он хочет выбрать модель и harness в едином UI и работать с одной задачей в контролируемом каталоге.

Результат: локальный воспроизводимый стенд; inference через LM Studio/llmster и LiteLLM; LibreChat — точка входа. Сначала доступен чат, затем агентный запуск с явным выбором OpenCode или официального DeepSeek Harness. Агенты не запускаются одновременно на запись в один workspace.

Не входит в MVP: установка LM Studio, управление моделями/видеодрайверами, публичный multi-tenant сервис, гарантия работоспособности любой модели с tool calling. Решения предварительные и требуют согласования пользователя.

PRD — черновик

Сценарий

Разработчик запускает сервер модели, поднимает стек, выбирает модель в LibreChat; позже выбирает harness и отправляет ему задачу в ограниченном workspace, после чего просматривает результат и журнал действий.

Требования

  • FR1: запуск/остановка Windows и Linux одной командой, без установки LM Studio проектом.
  • FR2: получить видимые серверу модели и настроить маршруты LiteLLM; обновление по запросу.
  • FR3: чат в LibreChat через LiteLLM с выбором модели.
  • FR4: выбор OpenCode или официального DeepSeek Harness для одной задачи без одновременной записи; продолжение задачи после переключения через явно сохранённое состояние.
  • FR5: документация по зависимостям, сети, WSL и устранению неполадок.
  • FR6: прозрачные статусы/ошибки и контроль доступа к workspace и выполнению команд.

Нефункциональные требования

  • NFR1: сервисы публично не экспонируются по умолчанию; секреты вне git.
  • NFR2: сохранение чатов при остановке; запуск агента с минимальными привилегиями.
  • NFR3: воспроизводимые версии и тесты интеграции до production.
  • NFR4: модель должна поддерживать нужные инструменты; результат и безопасность не гарантируются LLM.

Границы

FR1–3 и FR5 реализуются в первом срезе с необходимостью E2E проверки. FR4 и агентная часть FR6 — backlog. Сквозное сохранение состояния не означает перенос внутренней истории/памяти между разными harness: нужен общий артефакт задачи и явный handoff.

Архитектура и решения

Целевая схема

LibreChat → OpenAI-compatible adapter/orchestrator → [OpenCode | DeepSeek Harness] → LiteLLM → LM Studio/llmster. Альтернативный прямой маршрут чата: LibreChat → LiteLLM → LM Studio/llmster. На Windows модельный сервер работает на Windows, Docker — в Docker Desktop/WSL; на Linux модельный сервер на хосте. Связность пересекает границы namespace и должна проверяться отдельно.

Границы

Текущая реализация содержит только прямой маршрут. Custom endpoint LibreChat не является универсальным протоколом запуска внешнего агента. Будущему адаптеру нужны собственный API chat completions, соответствие streaming и модельной выборки, маршрутизация в контролируемые отдельные контейнеры, управление сессией, сохранение контекста и обработка ошибок. Возможен выбор harness через отдельные endpoint; смена endpoint сама по себе не переносит состояние. Общий task manifest, история handoff и состояние workspace — явный контракт, ещё не реализованный.

Агент запускается от непривилегированного пользователя в выделенном контейнере; workspace монтируется только после явного выбора, сеть ограничивается, Docker socket и секреты других сервисов не предоставляются, запись сериализуется per workspace. Контейнер не гарантирует надёжную изоляцию: нужны усиление, подтверждение опасных действий, стратегия отката и аудит. Доступ к LiteLLM через отдельный ограниченный ключ — задача следующего этапа. Защита от prompt injection не гарантируется.

Решения и риски

LM Studio на Linux или официальный llmster вместо стороннего сервера; /v1/models для единого формата. LiteLLM отвечает за настройки подключения. Список обновляется вручную; JSON-конфигурация совместима с YAML. MongoDB и Meilisearch — зависимости LibreChat. В текущем compose нет RAG. Секреты создаются локально, порты публикуются на loopback. Образы LibreChat и LiteLLM пока не зафиксированы по digest; требуется закрепление и compatibility test. DeepSeek Harness developer preview, API меняется; надо проверить реальный поддерживаемый способ подключения к совместимому провайдеру и интеграции агента до реализации. Модель может не поддерживать tools.

Техническое исследование: интеграция harness

Проверено по официальной документации 2026-11-08:

  • OpenCode V2 предоставляет экспериментальный HTTP API с POST /api/session, POST /api/session/{sessionID}/prompt, /api/event и API разрешений: https://opencode.ai/docs/api . Прежние записи про /session и /session/:id/message относятся к V1 и для новой интеграции не используются. Рекомендуемый клиент: https://opencode.ai/docs/build/client . Адаптер должен связывать жизненный цикл сессии, подтверждения прав и события со спецификацией LibreChat; API не является сам по себе OpenAI Chat Completions. Контракт экспериментальный и должен быть зафиксирован вместе с версией.
  • В V2 правила называются permissions, с действиями shell, edit, read и external_directory; правила агента могут переопределять общие. Стандартная политика разрешает много операций, в том числе внешние каталоги: https://opencode.ai/docs/permissions . Один запрет в конфигурации не заменяет изоляцию и ревизию итоговой политики.
  • Официальный DeepSeek Harness @deepseek-ai/dsh — developer preview с потенциально несовместимыми изменениями: https://github.com/deepseek-ai/deepseek-harness . Каталог конфигурации описывает отдельный API gateway и маршрут модели https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/config-catalog.md . Наличие возможного провайдера OpenAI-compatible не подтверждает совместимость всего пути LibreChat → harness → LiteLLM.
  • Официальный Python SDK DSH поддерживает API DeepSeekHarness.run, но профиль sdk-minimal использует danger-full-access и по умолчанию включает отправку событий журнала при DeepSeek-запросах; требуется отдельный профиль/patch, проверка утечек и реально изолированный контейнер: https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/user/guide/python-sdk.md . Нельзя подключать этот профиль к пользовательским файлам как к песочнице.
  • Оба harness должны быть зафиксированы по версиям и протестированы с моделью, поддерживающей tool calling. Нельзя запускать инструменты с правами пользователя или в общем workspace только потому, что сервис контейнеризирован. Выбор режима подтверждения, отсутствие конкурирующей записи и обработка долгих запросов обязательны до включения агентного маршрута.

Вывод: подготовлено локальное хранилище handoff с транзакциями как основа для будущего orchestrator; оно не претендует на выполнение S2.2 или на полную защиту S2.3/S2.4. Нужны проверка API DSH на выбранной версии и реальные интеграционные испытания.

Epics и stories

E1: локальный чат (FR1, FR2, FR3, FR5)

  • S1.1 Оператор запускает и останавливает стек на обеих ОС; данные сохраняются. AC: одна команда, нет автоматической установки model server, stop не удаляет тома.
  • S1.2 Оператор обнаруживает модели. AC: /v1/models, безопасное экранирование ID, понятная ошибка пустого списка, повторный refresh.
  • S1.3 Оператор отправляет чат из LibreChat через LiteLLM. AC: endpoint и модель доступны, запрос реально доходит до LM Studio; проверить интеграционным тестом.

E2: безопасные агенты (FR4, FR6)

  • S2.1 Проектировщик проверяет версии API OpenCode и официального DSH, протоколы и поддержку LiteLLM; фиксирует рабочие версии и ограничения.
  • S2.2 Пользователь выбирает один из harness в LibreChat. AC: реальный запуск выбранного harness, поток событий и ошибки видны; нет фиктивной имитации.
  • S2.3 Пользователь передаёт задачу другому harness. AC: общий task manifest, handoff и сохранённый workspace; блокировка конкурентной записи и явное подтверждение перехода.
  • S2.4 Оператор ограничивает инструменты. AC: непривилегированный runtime, без Docker socket, allowlist workspace, проверка доступа и аудит.

E3: воспроизводимость и качество (NFR1–4)

  • S3.1 Закрепить версии/digest, описать обновление, провести тесты на Windows/WSL и Linux.
  • S3.2 Добавить автоматизированные end-to-end тесты, тесты ошибок сети, streaming, tool calling и проверку защиты границ.
  • S3.3 Выделить ограниченные ключи, отказоустойчивость, резервное копирование и политику хранения.

Проверка готовности

Статус: CONCERNS. Разрешён только ограниченный E1 prototype. E1 S1.3 требует проверки на целевой машине; сквозная проверка не заменяется unit-тестами. E2 заблокирован до проверки API DeepSeek Harness и решения UX/безопасности. Не определены политика подтверждения команд, поддерживаемые модели и переносимый формат задачи. Версии плавающих образов закрепить до production. Артефакты подготовлены по мотивам BMAD, без утверждения о выполнении официальных workflow или формального sign-off.

Критические ограничения

DeepSeek SDK

Официальный sdk-minimal использует danger-full-access:

  • Агент может модифицировать любой файл
  • Агент может выполнять любые команды
  • События журнала отправляются в DeepSeek

Нельзя подключать к пользовательским файлам как к песочнице.

LibreChat интеграция

Custom endpoint LibreChat — это OpenAI-совместимый API, не универсальный протокол запуска агента. Реальный запуск harness через LibreChat не подтверждён документацией.

Версии образов

Используются плавающие теги (latest, main-stable). Для production требуются фиксированные digest.

Квоты LiteLLM

Отдельные ключи генерируются, но без базы данных LiteLLM они не ограничены.

Что необходимо для production

1. Фиксация версий всех образов (digest или exact tag) 2. Настройка базы данных LiteLLM с квотами и ограничением моделей 3. Разработка изолированного профиля DeepSeek без danger-full-access 4. Integration-тесты с реальным LM Studio и LibreChat 5. Ревью политики разрешений OpenCode перед запуском реальных задач 6. Мониторинг и аудит выполнения задач
