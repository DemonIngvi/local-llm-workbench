# Техническое исследование: интеграция harness

Проверено по официальной документации 2026-11-08:

* OpenCode V2 предоставляет экспериментальный HTTP API с `POST /api/session`, `POST /api/session/{sessionID}/prompt`, `/api/event` и API разрешений: https://opencode.ai/docs/api . Прежние записи про `/session` и `/session/:id/message` относятся к V1 и для новой интеграции не используются. Рекомендуемый клиент: https://opencode.ai/docs/build/client . Адаптер должен связывать жизненный цикл сессии, подтверждения прав и события со спецификацией LibreChat; API не является сам по себе OpenAI Chat Completions. Контракт экспериментальный и должен быть зафиксирован вместе с версией.
* В V2 правила называются `permissions`, с действиями `shell`, `edit`, `read` и `external_directory`; правила агента могут переопределять общие. Стандартная политика разрешает много операций, в том числе внешние каталоги: https://opencode.ai/docs/permissions . Один запрет в конфигурации не заменяет изоляцию и ревизию итоговой политики.
* Официальный DeepSeek Harness `@deepseek-ai/dsh` — developer preview с потенциально несовместимыми изменениями: https://github.com/deepseek-ai/deepseek-harness . Каталог конфигурации описывает отдельный API gateway и маршрут модели https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/config-catalog.md . Наличие возможного провайдера OpenAI-compatible не подтверждает совместимость всего пути LibreChat → harness → LiteLLM.
* Официальный Python SDK DSH поддерживает API `DeepSeekHarness.run`, но профиль `sdk-minimal` использует `danger-full-access` и по умолчанию включает отправку событий журнала при DeepSeek-запросах; требуется отдельный профиль/patch, проверка утечек и реально изолированный контейнер: https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/docs/user/guide/python-sdk.md . Нельзя подключать этот профиль к пользовательским файлам как к песочнице.
* Оба harness должны быть зафиксированы по версиям и протестированы с моделью, поддерживающей tool calling. Нельзя запускать инструменты с правами пользователя или в общем workspace только потому, что сервис контейнеризирован. Выбор режима подтверждения, отсутствие конкурирующей записи и обработка долгих запросов обязательны до включения агентного маршрута.

Вывод: подготовлено локальное хранилище handoff с транзакциями как основа для будущего orchestrator; оно не претендует на выполнение S2.2 или на полную защиту S2.3/S2.4. Нужны проверка API DSH на выбранной версии и реальные интеграционные испытания.
